**JIT finding.** The first 0.4.0 benchmark run showed one fork in five or six running the vector NT GEMM
about 60x slower (24 ms against 0.4 ms). `-XX:+PrintCompilation` showed the cause: C2 could not OSR-compile
a loop that runs with a non-empty operand stack ("OSR starts with non-empty stack"). HotSpot then fell back
to tier 1 (C1, no Vector API intrinsics) and never recompiled. The loop came from a Scala `inline def`
expanded inside `cd(i) += alpha * sumLanes(...)`. 0.3.0 ships the same construct, so it can hit this at
random. 0.4.0 removes such loops (see `docs/DEVELOPING.md`); 6-fork NT runs and the vector25 test suite now
show no OSR bailouts in numscala code. The same issue had made the first 2x4 NT block look slower than 1x4.

## Parallel GEMM (NS-CPU-001 §7.3)

`ParallelF32.gemmInto` splits C's rows into 4-row-aligned chunks. With 6 workers it reaches 2.9–4.7x and
about 200–270 GFLOP/s. Going to 12 or 24 workers helps only the larger products (TN 384x768x512: 5.7x
at 12 workers) and loses a little elsewhere. 24 workers means SMT siblings, which share FMA units, and
128-row products only have 32 row blocks to hand out. The scaling is far from linear: the B panel is
re-read by every worker, so memory/L3 bandwidth, not FMA throughput, limits it. For a model that already
parallelises across sequences, intra-GEMM parallelism is most useful on the large weight-gradient (TN)
products. Results are bit-identical for every worker count (`F32KernelContract`).
